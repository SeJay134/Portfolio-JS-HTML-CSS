2. FINDINGS IN THE CURRENT PROJECT

F01 [P1, UI] index.html/css/index.css: the portrait and navigation occupy a
    permanent area. On small screens, this becomes a fixed top panel with a
    height of 130/160px. There is no hamburger button or controlled drawer.
F02 [P1, UI] Styles contain repeated media-query blocks, fixed dimensions,
    min-width rules, and large offsets. Examples include margin-left:418px
    for message actions and negative footer offsets. These create risks at
    intermediate widths; confirm specific overflow cases in a browser.
F03 [P1, UI] Multiple font families, decorative shadows, and translucent headings
    weaken the hierarchy. Confirm contrast concerns with actual measurements.
F04 [P1, projects] js/index.js requests /users/sejay134/repos in the browser.
    There is no curated selection of featured work or API pagination.
    Every preview assumes main/preview.png. Missing homepage values become
    href="No website available.". Descriptions depend on hover tooltips,
    which are inconvenient on touch devices.
F05 [P0, contact] Leave a Message only creates a DOM entry and logs to console.
    It does not send or persist a message. Name/email/message values are inserted
    through innerHTML, an unsafe HTML-injection path even with local-only input.
F06 [P1, accessibility] #chat_button is a clickable div without native button
    behavior. Chat lacks a dedicated Send button and complete focus handling.
    Form inputs lack real label elements; a label attribute is not a substitute.
    Social links reuse id="link" and contain icons without accessible names.
F07 [P1, chat] fetch does not check response.ok; 400/429/500 responses can appear
    as "No response". There is no timeout, stop/retry, pending guard, or response
    ordering protection. Submission requires Enter. Error text hardcodes hours.
F08 [P0, backend] llm/app.py stores chat_history globally within the process.
    The regular chat path can use another visitor's messages. This is a verified
    storage-design issue, not evidence of a specific observed data leak.
F09 [P0, API] str(data.get(...)) runs before type validation, converting numbers
    and objects to strings. A nonempty JSON array has no .get and can cause 500.
    The 300-character limit, MAX_CONTENT_LENGTH, and rate limit already exist;
    preserve these protections.
F10 [P1, configuration] js/config.js hardcodes an ngrok URL. It recognizes
    localhost but not 127.0.0.1. Flask currently uses port 5002. Separate
    environment URLs from source code and document local/public workflows.
F11 [P1, RAG] Regular chat and run_rag use different instructions. RAG does not
    receive SYSTEM_PROMPT or history and combines instructions/context into a
    user message. Router uses English keywords and a fixed L2 threshold of 1.4.
    Retriever does not discard FAISS sentinel id=-1 when too few results exist.
F12 [P1, startup] Retriever loads its index during app.py import, requiring
    index/metadata files beforehand. README describes rag_text.txt, whereas
    indexer reads data/base/. watcher.py is entirely commented out.
    The repository has no tracked requirements/pyproject, package.json,
    automated tests, or CI configuration.
F13 [P1, behavior] js/index.js forces scrollTo(0,0) on load and focusin and changes
    zoom/overflow. This can interfere with deep links and mobile input.
F14 [P2, payload] p5.js is loaded for a 64x64 button animation. The tsParticles
    bundle is also loaded although initialization is disabled. Review and remove
    legacy chat JS/CSS variants after regression checks.
F15 [P1, SEO] Current index.html lacks a standard meta description, OG card,
    and canonical URL. A page title already exists and should be preserved.

3. LAYOUT OPTIONS AND COMPONENT PLACEMENT

Option A: recommended left drawer overlay.
  Header, 64-72px: a Menu button and name/monogram on the left; theme and Contact
  on the right. Center the main area within approximately 1120-1200px.
  Navigation starts closed on every screen and opens from the left on click.
  Benefits: more room for projects, consistent desktop/mobile behavior, and no
  text-width jump. Tradeoff: sections are hidden. Compensate with Projects and
  Contact hero actions and a visible "Menu" label next to the icon.

Option B: a 64-72px desktop rail that expands to 280-320px.
  The collapsed rail shows section icons with accessible names. The expanded
  panel overlays content. Mobile uses Option A. This creates a stronger app-like
  appearance but permanently occupies some horizontal space.

Option C: a desktop push-menu that shifts the main area.
  Use only on wide screens with a deliberately allocated grid column.
  Drawbacks: more responsive complexity, changing line lengths, possible jumps.
  Do not choose this for the first release; evaluate Option A with real visitors.

Recommended page order:
  1) Hero: name, concise specialization, 1-2 sentences about the value of the
     work, View projects and Contact actions, and Resume if a file is available.
     Desktop: roughly 60% text and 40% portrait/small scene. Mobile: text and
     actions first, followed by a compact portrait.
  2) Featured Projects: 3-4 selected case studies, followed by All projects.
  3) Skills: Web / Python & Data / AI & RAG / Tools, linked to examples.
  4) Experience: a compact timeline with 2-3 meaningful points per role.
  5) About: brief personal context and working approach.
  6) Contact: email/LinkedIn/GitHub and a working form if a backend is available.
  7) Footer: copyright, contacts, and a back-to-top action.
  Keep chat accessible at bottom-right without covering Contact or safe areas.
  Avoid a public Messages list for private inquiries.

Project card:
  16:10 preview -> title -> problem/result in 2-3 lines -> 3-5 technology tags
  -> Live demo when available + Code + Details. Details explain personal role,
  solution, limitations, and a verifiable outcome. Do not invent impact metrics.
  Desktop: 2-3 columns; tablet: 2; mobile: 1. A portfolio should curate GitHub work.
  Present the AI/RAG assistant's architecture as an engineering case study.

5. PHASE 1: FIX LOGIC BEFORE REDESIGN
Categories: API, security, contact, reliability. P0. Estimate: 2-4 days.
Dependency: Phase 0.

Tasks:
[ ] Remove global history. The first safe version can be stateless. Then introduce
    server-side sessions with unpredictable identifiers, TTL, bounded history,
    and clearing. Multiple workers require shared storage. Do not expose another
    session's history through an arbitrary client-supplied identifier.
[ ] Validate JSON as an object and message as a string before conversion. Apply
    trimming, length limits, and consistent JSON errors for 400/413/429/503.
[ ] Add model timeouts, generation concurrency limits, a central error handler,
    and request_id. Do not report success when model execution fails.
[ ] Configure trusted origins and correct client IP handling behind the proxy.
    CORS is not authentication. Production rate-limit storage must work across
    workers. Reduce logging of conversation contents.
[ ] Replace user-controlled innerHTML with textContent and safe URLs.
    If Markdown is added later, sanitize its rendered output.
[ ] Contact: provide mailto immediately. Connect a real form to a chosen delivery
    backend with validation, limits, and spam protection. Until then, remove any
    false impression that a message was sent. Do not publish visitor emails or
    messages. Show success only after API confirmation.
[ ] Fix invalid homepage links, image fallbacks, and project error handling.

Tests and acceptance:
  pytest with mocked Ollama: empty input, number/null/array/object message values,
  oversized requests, 429, timeout, and model failure return expected JSON/status.
  Independent sessions A/B: an A-only marker never reaches B's model request.
  Test clearing, TTL, concurrency, and multiple workers for history isolation.
  Malicious HTML displays as text without executing.
  Contact: successful delivery to a test receiver, delivery failure, repeated submit.

6. PHASE 2: DESIGN SYSTEM AND LEFT HAMBURGER MENU
Categories: UI, navigation, responsive design, accessibility. P1.
Estimate: 2-4 days.
Dependency: Phase 0; complete P0 fixes before public release.

Design:
[ ] Introduce CSS tokens for background, surface, text, muted text, border, accent,
    spacing, radius, shadow, z-index, and duration. Apply themes through tokens.
[ ] Use one readable sans-serif family, optionally a monospace face for small
    technical labels. Body: 16-18px, line-height 1.5-1.65, text width 60-75ch.
    Use clamp() for H1 and clear headings instead of heavy shadows/cursive titles.
[ ] Suggested light palette: #F8FAFC / #FFFFFF / #0F172A; dark palette:
    #0B1120 / #111827 / #E5E7EB. Select blue accents per background and test contrast.
[ ] Spacing: 8/16/24/32/48/64px; radii: 12-16px; restrained borders/shadows.
    Left-align paragraphs rather than justifying them on narrow screens.
[ ] Remove fixed offsets and excessive min-width. Use mobile-first grid, max-width,
    gap, and minmax(0,1fr). Check intermediate widths continuously.

Drawer specification: the user's primary priority.
[ ] Use a native top-left button with a minimum 44x44px target, aria-expanded,
    and aria-controls. The hamburger icon changes to a close icon.
[ ] Desktop width: 280-320px; mobile: min(86vw, 320px). Use 100dvh, internal
    scrolling, and safe-area padding. Keep the internal Close button visible.
[ ] Top: mini portrait/name. Navigation: Home, Projects, Skills, Experience,
    About, Contact. Bottom: Theme, Resume if available, GitHub/LinkedIn.
[ ] Open with click/touch/Enter/Space. Close with Close, Escape, backdrop, or
    section selection. Opening must not depend on hover.
[ ] Animate translateX(-100%) to 0 and backdrop opacity over 200-260ms.
    Avoid width/left/layout animation. Respect prefers-reduced-motion.
[ ] Option A is a modal dialog containing normal nav links, not role=menu.
    On open, move focus inside, contain Tab, make background content inert,
    and lock background scrolling. On dismiss, restore scroll and trigger focus.
    After section selection, close and focus that section's heading.
[ ] Closed navigation must be unavailable to Tab and screen readers; translate
    alone is insufficient. Coordinate hidden/inert with transition completion.
[ ] Highlight the active section using IntersectionObserver and aria-current.
    Preserve href anchors, header-aware scroll-margin-top, and Back/Forward.
[ ] Use a single overlay owner: opening modal navigation minimizes/closes chat
    while preserving its draft. Avoid competing focus traps.
[ ] Provide System/Light/Dark theme selection, persistence, and a correct first frame.

Tests and acceptance:
  Playwright: all open/close methods, rapid clicks, resizing while open, anchors,
  scroll restoration, and no stuck scroll lock.
  Keyboard and VoiceOver: accessible names, Tab order, Escape, and focus return.
  Hidden links cannot receive focus. Combine automated axe with manual checks.
  320-1440px, landscape, 200% zoom: no lost content or horizontal scrolling.
  Reduced motion: fully functional without movement. Both themes remain readable.

8. PHASE 4: MODERN CHAT INTERFACE AND RAG QUALITY
Categories: chat UX, API, AI, operations. P1/P2. Estimate: 3-6 days.
Dependency: Phase 1 and Phase 2 visual tokens.

UI:
[ ] Desktop: approximately 380-420px wide, bounded by viewport dimensions, with
    "Ask about Sergei," a purpose statement, Close, and New conversation.
    Mobile: nearly full-screen with 100dvh, safe areas, and keyboard handling.
[ ] Add a clear touch-friendly Send button. Enter submits; Shift+Enter inserts
    a newline. Handle composition events. Match the server's 300-character limit.
[ ] Model idle/sending/receiving/success/error/offline states. Add waiting feedback,
    retry that retains text, timeouts, and duplicate-submit protection.
[ ] Offer prompts such as "What projects has Sergei built?", "Python experience?",
    and "How can I get in touch?". Avoid "Ask me anything" for a scoped assistant.
[ ] Autoscroll only when the visitor is already near the bottom; otherwise show
    a New response indicator. Use role=log/aria-live for completed new answers
    without announcing every streamed token.
[ ] Obtain availability from health/readiness with cache/backoff rather than
    hardcoded operating hours. Offer projects/contact when the server is offline.
[ ] Desktop non-modal chat permits normal Tab exit. Mobile modal chat follows
    dialog rules. Minimization preserves drafts; clearing removes server history.
[ ] Add streaming after the JSON API is reliable. For POST, use fetch ReadableStream
    with a defined event protocol; native EventSource does not directly POST a body.
    Stop aborts the client request. Implement server generation cancellation
    separately; AbortController alone does not guarantee Ollama stops computing.

RAG and backend:
[ ] Unify chat/RAG answer policies and use a separate system role. Treat retrieved
    context as data, not instructions. Answer in the current message's language.
[ ] Follow-up questions use only the current session's history. Missing knowledge
    produces an honest fallback and contact link, not invented skills/employers.
[ ] Validate FAISS ids >=0 and <len(chunks), empty indexes, ntotal, and metadata
    compatibility. Resolve data paths from the project root; replace indexes atomically.
[ ] Establish one knowledge source consistent with public projects and the resume.
    Return a clear failing exit code when rebuilding the index fails.
[ ] Calibrate threshold/top_k against labeled English/Russian questions.
    IndexFlatL2 returns squared L2 distance, not confidence percentages.
    Rebuild indexes and recalibrate after changing embeddings or normalization.
[ ] Evaluate all-MiniLM-L6-v2 on Russian questions. Choose a multilingual alternative
    based on evaluation results rather than popularity.
[ ] Return verifiable project/section links from metadata. Do not expose internal
    paths, system instructions, or raw similarity scores.
[ ] Provide stable production HTTPS hosting, WSGI/process supervision, model/index
    readiness, queues/limits, and minimal operational logs without conversations.
    Portfolio content and contact must remain usable independently of AI uptime.

Tests and acceptance:
  Mock API: 200, 400, 413, 429 with Retry-After, 500, invalid JSON, offline, timeout,
  slow/interrupted streams, and out-of-order responses. Drafts are retained.
  Maintain 30-50 English/Russian regression questions covering biography, projects,
  contacts, paraphrases, follow-ups, unknown facts, unrelated requests, instructions
  embedded in context, and attempts to retrieve another session's history.
  Measure retrieval recall against labeled sources separately from answer accuracy.
  Release target: >=90% correct answers on supported evaluation questions and
  zero invented facts in unknown-information tests. These are acceptance criteria,
  not guarantees of error-free answers for every possible query.
  Record p50/p95 time to first output and full response on target hardware.
  Choose load limits after measurement; do not promise unmeasured fixed latency.

9. PHASE 5: INCREMENTAL REACT + TYPESCRIPT MIGRATION
Categories: architecture, tooling, testing. P2. Estimate: 3-6 days.
Dependency: stable UX/API from previous phases.

Technology choice:
  React + TypeScript + Vite is the recommended moderate foundation while keeping
  Flask/Ollama. React does not automatically fix security issues.
  CSS Modules plus tokens are sufficient. Tailwind is optional; do not introduce
  both styling approaches without a reason. Redux is unnecessary for this scale.
  If SEO-driven case-study pages/blogging become central, separately compare
  Next.js static generation and Astro with React components. A basic SPA does not
  automatically deliver server-rendered content. Avoid simultaneous migrations
  across multiple frameworks.

Sequence:
[ ] Add build scripts and pinned versions/lockfile; configure ESLint, TypeScript,
    and formatting. Choose and verify exact versions during implementation.
[ ] Define Project, Message, ChatResponse/ChatError, and environment configuration
    types. VITE_* variables are public: never put model/email/GitHub secrets there.
[ ] Migrate ChatWidget or NavigationDrawer as the first isolated React root.
    Disable the old DOM owner for that region to avoid duplicate listeners.
[ ] Migrate AppShell/Header/Drawer/ThemeToggle, Hero, ProjectGrid/ProjectCard,
    ExperienceTimeline, SkillsGroups, ContactForm, and Footer.
[ ] Extract the API client, useChat, useTheme, useActiveSection/useReducedMotion.
    Keep panel visibility with a common owner rather than unrelated flags.
[ ] Clean up requests, listeners, observers, timers, and WebGL on unmount.
    StrictMode must not cause duplicate submissions or animation loops.
[ ] Lazy-load chat and future 3D. Add ErrorBoundary for optional widgets.
    Anchor navigation does not require a router; introduce one for separate pages.
[ ] After parity checks, remove chat_old.js/chat_old.css/chat_new.css, duplicate
    DOM scripts, and unused dependencies. Keep the Flask backend separate.
[ ] Verify Vercel build/output, API routing, and deep links. Preserve working URLs.
    Release the frontend through a preview and retain a rollback deployment.

Tests and acceptance:
  Vitest + Testing Library: drawer, theme, form, chat, and filter interactions.
  MSW or equivalent API mocks for edge cases; pytest preserves backend contracts.
  Playwright: navigation -> project -> chat -> contact, both themes, mobile/desktop.
  Compare pre/post-migration capabilities; direct-page reloads and anchors work.
  React must not exceed the agreed initial JS budget without justification.

10. PHASE 6: ANIMATION, THREE.JS, AND MODERN DETAILS
Categories: motion, graphics, performance. P3. Estimate: 2-5 days.
Dependency: Phase 5 and passing performance/accessibility gates.

Level 1: implement first.
[ ] CSS transitions for navigation, buttons, and cards: 120-220ms, transform/opacity.
[ ] Subtle section reveals with IntersectionObserver. Content remains visible by
    default if JavaScript/observers fail. Do not hijack scrolling.
[ ] Card lift of 2-4px and restrained focus/hover treatments. Touch must not depend
    on hover. Smooth theme colors; reduced-motion mode avoids movement.
[ ] Replace the p5 chat-button animation with compact SVG/CSS if its effect does
    not justify the dependency. Avoid retaining three separate effects libraries.

Level 2: choose one distinctive Three.js scene.
  A. Neural constellation: a small cluster of nodes/links beside the hero, slow
     rotation, and slight pointer response. Recommended: relevant to AI projects
     while keeping text calm and readable.
  B. Geometric SL monogram: a simple 3D object without heavy textures in a dedicated
     hero region rather than behind the entire page.
  C. Interactive RAG architecture graph inside its case study, accompanied by an
     accessible HTML explanation. More useful than decorative 3D on every block.
  D. Full-page particle background: experimental only, with greater distraction
     and rendering costs. Prefer a CSS gradient for the first release.

Technical requirements:
[ ] Dynamically import after primary content; show a static poster/gradient first.
    With React, React Three Fiber is an option; direct Three.js is also valid.
    Introduce R3F only for the chosen scene, not for basic CSS transitions.
[ ] Use one canvas, an initial DPR cap around 1-1.5, adaptive particle counts,
    and no heavy postprocessing/shadows by default.
[ ] Pause the loop in hidden tabs or when the hero leaves the viewport. On unmount,
    cancel RAF and dispose of geometries/materials/textures/renderer resources.
[ ] Reduced motion, an economy mode, and a manual Effects off setting use a static
    background. WebGL failure/context loss must not break navigation or chat.
[ ] Decorative canvas: aria-hidden and pointer-events:none. Interactive scenes
    need a dedicated area, HTML alternative, and keyboard controls.
[ ] Disable effects after sustained poor performance on weaker devices.
    60fps desktop/30fps mobile are measurement targets, not advance promises.

Other modern features, ordered by value:
  P2: case studies with direct URLs, polished OG preview, accessible resume,
      remembered theme, and skeletons only for data that is actually loading.
  P3: View Transitions for filters/pages with fallbacks and reduced-motion support;
      English/Russian UI when translations and correct lang attributes are ready;
      Cmd/Ctrl+K navigation if the site grows, while retaining standard navigation.
  Defer PWA/service workers, visitor accounts, a CMS, and a heavy animation stack
  until a concrete use case exists. They add maintenance to a small portfolio.

Tests and acceptance:
  Disabled WebGL, context loss, reduced motion, hidden tabs, resize/orientation,
  and repeated mount/unmount preserve content and do not accumulate resources.
  3D stays within LCP/INP budgets; measure on a real midrange phone.
  Scrolling and chat typing remain responsive with effects enabled.
